# 探索処理の追加高速化（2026-10-09）

対象の正本は `/home/user/chess/alphazero_chess_v2`。比較元は2026-10-09のバッチ自己対局版。既存の800探索、ルートノイズ、学習ターゲット、対局結果の扱いを用いて比較する。

## 実装

1. `HistoryEncoder`で駒配置から作成した配列を再利用する。各探索のキャッシュ上限は2,048配置。キーはpython-chessの反復キーの最初の8要素（各駒種と双方の占有ビット）。この配列には手番、反復回数、キャスリング権、アンパッサン、手数は含まれず、それらは毎回別に計算する。同じ配置でも局面全体やニューラルネット評価を共有する処理ではない。
2. 展開する局面の合法手を一度生成し、終局判定と手の番号変換で共有する。75手・50手ルールの合法手存在条件は先に確認し、詰み・駒不足・ステイルメイト・反復・手数ルールの優先順位を維持する。
3. 終局した探索ノードの価値を保存し、再訪時の判定を省く。ノードは各探索内の経路に対応するため、異なる履歴同士を統合しない。
4. 候補比較で呼び出していたlambdaとvalueプロパティを、同じ計算順のループに置き換える。最大値が同点なら先に生成された手を選ぶ。Nodeにはslotsを使ってオブジェクトの負担も減らす。
5. 通常移動の出力番号を64×64の表で引く。黒側の向きはsquare XOR 56で変換。小駒への昇格は別処理。チェスの合法手以外の入力についても、表で扱えない場合は従来の変換を使う。
6. バッチサイズ別に入力メモリーを再利用する。今回の要求数より後ろの行をゼロにし、完了したdevice_getの後でのみ再利用する。推論精度とバッチサイズの選び方は既存版に従う。

## 検証

- 実棋譜48局と特殊局面の3,118サンプルで入力119面と終局判定が一致。履歴を戻す場合も確認。
- 手番2種類、出発64、到着64、昇格5種類の40,960入力で、出力番号または例外発生が従来と一致。
- CPU単独200探索、初期局面と50手ルール直前のルーク終盤で探索木4,950ノードの訪問回数・価値合計・事前確率が完全一致。
- CPUバッチ自己対局2局、64探索、12半手、シード90110/90111を新しく生成し、NPZの全項目が一致。12半手打ち切りはこの検証用ディレクトリだけの設定。
- GPUバッチ比較は8局面×800探索、8同時、ルートノイズあり、シード90100+局面番号。B50保存モデルとRTX 3060を使用。初期局面2つと実棋譜終局5半手前の6局面を使用する。各版3回、順番を交互にして測定。毎回ウォームアップ後に測る。バッチの要求順とサイズも同じ。

測定結果は `search_validation.json`、`search_validation.log` に記録する。各比較の探索木93,847ノードについて訪問回数・価値合計・事前確率、合法手の順番を比較し、推論呼び出し数も一致を確認する。`baseline_profile.txt` と `candidate_profile.txt` は200探索の処理内訳で、計測器による負荷を含むため通常の速度比較には使用しない。

これは短い探索試験。実際の1サイクル全体の高速化率、学習の強さへの効果は未測定。GPU計測には変動があるため、最大の改善倍率だけを全体の効果として扱わない。
