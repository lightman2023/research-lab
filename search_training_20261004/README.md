# 自己対局の探索50回・200回で学習を比較

## 目的

同じcycle 10から、自己対局の探索予算だけを変えて学習する。
200回探索で得た訪問分布を学習すると、モデルの手の予測・棋力・反復傾向が改善するかを見る。
今回の50対200の対戦結果は探索の効果であり、学習の効果は未確認。

## Windows GUIでの実行順

### Bのみ追加学習（2026-10-05）

`探索学習比較_B200を起動.bat` は5サイクル以降も続けられる追加学習GUIへ更新した。
現在の評価に使うcycle 5の保存モデルは固定し、Bのlatestと学習状態を更新する。
連続回数0は手動停止まで継続。正の回数なら、その回数だけ追加して停止する。
世代保存間隔は従来どおり変更でき、latestと学習状態は毎サイクル保存する。
一定学習率0.0001・温度1・探索200回・8局/サイクル・64更新を維持する。
評価対局との同時実行を許可したが、別の学習との重複起動は禁止。同じGPUを共有するため所要時間は伸び得る。
新しい比較GUIからもBの追加学習中に保存モデルの評価を開始できる。開いたままの旧GUIは起動時のコードを使うため、必要なら開き直す。
初回5サイクルの比較結果・元設定は保持し、追加分は`continuation_protocol_20261005.json`に条件を記録。
今回、6サイクル目から開始するよう自動起動。以降の停止・再開はBのGUIで操作する。

### GPU関連エラー後のCPU比較（2026-10-05）

GPUで開始モデル対B cycle5を比較中、1局目の途中で比較プロセスが終了した。失敗した棋譜は0局（空ファイル）、設定JSONは保存。
WSLのdxg GPU処理の異常・割り当て失敗（Ioctl -12）を確認。GPU同時実行との因果やハードウェア・ドライバーの故障は未確定で、メモリ不足を断定しない。
比較GUIにcpu/gpu選択を追加し、CPUを初期値にした。学習はGPUのまま継続。
`開始モデルとBをCPUで比較.bat` は、元の温度1cycle10対B cycle5、両側200探索、12局、上限512半手を選択済み。
比較のモデル・探索数は固定し、両側をCPUで評価。CPUとGPUの浮動小数演算差で手が変わる可能性があるため、今回の再実行はCPU評価として記録し、旧GPU対局と同条件とは扱わない。
`arena.py --device cpu` はJAXの初期化前にJAX_PLATFORMS=cpuを指定。実デバイスをloadingイベントと設定JSON、CPU/GPUを棋譜へ記録。
GUIは失敗時の終了コードを省略せず記録するようにした。
GPU学習中にCPU・200探索・上限20半手の小規模1局を実行し、CPUのみの初期化と対局完了を確認（約34秒）。これは本評価の勝敗として集計しない。
`cpu_smoke_validation.json`に確認結果。CPU版GUIで12局の本比較を自動再開する。
設定の根拠はJAX公式Configuration OptionsのPlatforms節：https://docs.jax.dev/en/latest/config_options.html#jax-platforms （本文確認済み）。

### 個別に実行する場合

1. `C:/Users/User/Desktop/chess_v2/探索学習比較_A50を起動.bat` を開き、「学習1サイクルを実行」。
2. 終了後、`探索学習比較_B200を起動.bat` で同じく1サイクルを実行。GPU実行は一つずつ。
3. 両方のログのMONITOR、エラー、所要時間を確認。価値ヘッドの不活性局面が検査集合の10%以上なら監視停止。停止が出た場合は続行せず原因を確認。
4. 各GUIの「連続学習を開始」で、残り4サイクルを一つずつ実行する。累計5で停止。初回に連続ボタンを押しても1サイクルで止まる。
5. `探索学習後のモデルを比較.bat` でA50・B200のcycle 5を対戦。評価は両側200探索、24局、12開始局面で白黒交換、上限512半手。
6. 既存比較GUIから開始モデル（いずれかのcycle 0、元の温度1cycle 10と同一）と各終了モデルも選べる。評価条件は両側200にそろえる。

比較結果だけでなく、モデル自体が強くなったかは開始モデルとの比較も必要。
初回1サイクルは設定・再開・監視・実際の所要時間を見る試運転であり、効果判定には使わない。
24局の結果が全て引き分け、または打ち切りが多い場合は強さの改善を断定しない。

## 共通条件

- 保存先 `/home/user/chess/alphazero_chess_v2/experiments/search-budget-20261004/{A50,B200}`。
- 共通開始点：温度1実験cycle 10、学習状態2880更新、160局の自己対局データ。評価棋譜は学習へ入れない。
- 一サイクル8局、2並列、64更新、batch 64、一定AdamW学習率0.0001、温度1、root noise α0.3・混合率0.25、上限512半手。
- A50：一手50探索、B200：一手200探索。5サイクルで各40局・320更新、予定最終3200更新。
- 学習教師方策は未加工の訪問割合。勝敗教師は既存終局規則。反復禁止・引き分け罰則・駒得の教師を追加しない。
- 同じseed設定で開始するが、生成された局面・ゲーム長・サンプル抽出は異なる。新データや抽出バッチが同じという意味ではない。
- 元データに含まれる上限打ち切り2局も同じ条件で引き継ぐ。この扱いは独自の既存実装であり、AlphaZeroの実終局結果と同一とは扱わない。新たな上限打ち切りも別に数える。
- 更新状態を両条件へコピーし、学習状態をリセットしない。コピーしたデータにはcarried接頭辞を付け、新実験のcycle別集計との混同を防ぐ。
- 世代保存間隔は変更可能。latest/stateは毎サイクル、有限実行の終了モデルも保存する。

- 各サイクルで固定129局面と学習データの128局面を監視。不活性割合10%は独自の診断用閾値。

- `configuration.json`、`carried_data_manifest.json`で設定・コピー元・SHA256を記録。元実験は保持。

## 準備段階の確認結果

- A/Bの160局全ファイル、モデル、学習状態はSHA256一致。元実験のモデル・学習状態も保持。
- 両条件の初期検査は不活性0。GPU推論の数値差は最大約0.0000196で、モデル・入力のハッシュ差ではない。浮動小数の検査は許容差を使って記録した。
- 別の確認用コピーで実際に1更新し、2880から2881への再開を確認。本実験A/Bは2880更新のまま。
- Windows Tkで両学習GUIを初期化。長い処理を置き換えた確認で、初回1停止・累計5停止・最終モデル保存・確認対局データの分離・探索数の伝達を確認。
- 学習後比較GUIに両条件を追加し、両側200探索と未完成モデルを誤って代用しないことを確認。
- `validation_results.json`、`controller_validation.json`、`entrypoints_validation.json`、`cycle_guard_validation.json`に記録。
- 本実験の自己対局・1サイクル試運転・5サイクル学習・最終対戦はまだ実行していない。200探索の実際のサイクル所要時間と学習効果は未確認。
